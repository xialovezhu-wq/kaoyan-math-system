# 数学每日复习与学习后旧题筛选合同

## 权威数据

- 考试日期的唯一权威入口是 `数学一回滚复习系统/学习进度.json` 顶层 `exam_date`，当前为 `2026-12-20`。
- 个人错因的唯一权威来源是正式错题卡的 `wrong_point` 和 `method_gap`。
- `错题知识网络/生成/wrong_questions.json` 是可重建的派生快照，不得与正式卡竞争真源。学习后旧题筛选会校验派生错因版本与正式卡一致。
- 长期错点 anchor 的到期资格只来自规范错题复习单元的 `下次复习日期`；该日期不直接指定实际交付题。

## 错因证据来源

`method_gap.evidence_origin` 只允许：

- `user_confirmed`：用户作答过程、第一错步或明确复发证据直接确认。
- `model_inferred_from_solution`：仅根据题面或解析提炼的正确路线，不是个人错因。
- `pending_user_confirmation`：候选断点仍需用户确认。

历史卡缺少字段时读为 `legacy_unclassified`，不做全库迁移。宽泛知识点、粗章节、正确解析路线、方法卡 ID 或动作分类标签单独相同，都不能证明命中同一个人错因。知识点可以在精确候选不足时作为明确标注的补位依据，但不能因此升级为个人错因证据。

## 活跃错点生命周期与两个七天窗口

- 活跃错点窗口只读取目标日前近 7 天内的正式做错 occurrence。只有仍未被更晚正确证据消除的 occurrence 才能成为当天 anchor；窗口外历史继续保留，但不自动进入当前活跃集合。
- 更晚的一次可验证正式独立作答，若评分为 4～5 且能证明同一具体错点、同一动作断点，或两张正式卡共同持有同一个 `knowledge` 标签，可以只把对应 occurrence 从派生活跃集合中移除；一次明确绑定该 anchor 的 `knowledge_fallback` 通过也适用。不得删除或改写正式卡的 `wrong_point`、`wrong_history`、复发计数、调度事件或历史成绩。
- 仅有自由文本粗章节、正确解析路线、提示后完成、评分 0～3、来源版本无法验证或同日没有可靠顺序时，证据不足，不自动消解。知识点级消解不等于证明同一方法断点，也不推进长期阶段；后续若出现新的正式做错 occurrence，应按新事件重新激活。
- 交付去重窗口独立于活跃错点窗口。实际交付题默认必须在目标日前超过 7 天没有新增、做错、复做、评分、入选/投递或更新；恰好第 7 天仍属于排除窗口，anchor 原题也受该门禁约束。
- 代理题评分会更新 anchor 的调度状态，但不能据此刷新 anchor 原题的交付活动日期。卡片活动只归属实际 `delivered_card_id`；最近七天 occurrence 已被正确覆盖而长期阶段仍到期时，使用独立的 `formal_due_proxy_*` 模式，不计入 `active_gap_total`。
- 永久交付门禁独立于上述两个窗口。实际 `delivered_card_id` 一旦有可验证的无提示独立做对证据，就永久不再作为任何 warmup 模式的交付题；后来降级、低分或再次做错不撤销。结构化评分只认 4～5 分；3 分这一数值本身可能来自提示后完成，不能触发。历史文本必须明确证明整题无提示、独立或闭卷；用户本人明确说当前题“做对了”按其用词约定也计入。局部正确、提示后完成或系统自行推断均不触发。该卡仍可作为不对用户暴露的内部 anchor，改用其他从未独立做对的旧题检查相关错点。

## 学习前队列

`scheduler.py warmup --date YYYY-MM-DD [--count N]` 按 anchor 与交付题两层选择：

1. anchor 层只包含 `下次复习日期 <= 当天`、且活跃 occurrence 尚未被更晚正确证据消除的规范错题单元。到期日表示错点从该日开始需要检查，不代表直接投递 anchor 原题。
2. anchor 超过容量时，按动态优先级、复发次数、掌握度、错误次数、逾期天数、具体错因证据价值和稳定 ID 排序。
3. 对每个入选 anchor，先从通过交付去重且唯一正式入库的旧题中查找同一具体 `wrong_point`、第一错步或 `method_gap`；这些题标为 `exact_gap`。交付卡不要求已有自己的长期复习单元，正式卡身份与来源版本通过即可参与；评分仍只写 anchor 单元。
4. 没有精确候选时，才按两张正式卡共同持有的 `knowledge` 标签选择旧题，标为 `knowledge_fallback`。共同标签允许较宽泛，但不能由模型根据自由文本章节临时推导父级关系，也不能只凭弱关系分或解析路线凑题；该层不能声称同一用户错因、同一方法断点或同方法复发。
5. 同一实际交付题不能在同一队列重复出现。精确与知识点候选都不足时少于请求数量，不采用近 7 天题补足，也不生成、改写或合成任何数学题。
6. 已被正确证据消解的近期 occurrence 不再作为近期错点机械重推。若 `exact_gap` 成功另行产生了后续长期到期日，而原题仍在交付窗口内，才以 `formal_due_proxy_exact` 继续长期阶段；它与近期错点池分开。未推进长期阶段的 `knowledge_fallback` 覆盖不会导致每天重复代理投递，原题达到第 8 天后仍可按正式到期规则独立检查。

公开 Markdown 只显示实际交付题的正式 ID、来源和必要的队列身份，不显示 anchor 错因、知识点、目标方法或解析。`.internal.json` 必须分别保存 anchor 的正式 ID、复习单元 ID、到期日、活跃 occurrence、正式卡和单元版本，以及实际交付题的正式 ID、正式卡版本、匹配层级和选题理由。队列题统一通过 `score-warmup` 提交：`exact_gap` 或直接到期检查可以按正式延迟复习规则推进 anchor 单元；`knowledge_fallback` 做对只消除该派生活跃 occurrence，不增加长期成功次数或推进长期阶段。两种模式都不得顺带修改实际交付题对应的其他单元。

队列 ID 对日期、模式、数量、选中 ID、正式卡版本、单元版本和配置做稳定哈希。同一日期、模式和请求数量的队列一旦正式生成，后续评分或候选规则变化都不得重算并覆盖它；重跑在核验公开页、内部包与日志身份一致后返回 `noop`。锁内重读、原子替换和 JSONL 事件 ID 防止并发重复。`--dry-run` 不创建锁、输出或日志。

## 学习中快速入库与夜间正式收口

用户在学习过程中明确要求把当前题入库、记录复发、更新或标记掌握候选时，默认只追加 `快速入库事件.jsonl` 的 source-backed capture；正式卡、wrongnet、定点回滚、关系提案和 Wiki 统一留到夜间批次。完整合同见 `schema/quick_intake_events.md`。

晨间交付题必须先完成准确 `score-warmup`，再让 capture 引用该稳定评分事件。capture 认证实际 `delivered_card_id`，不能把 anchor 卡误当本轮作答题。`supplemental_training` 不制造长期评分事件，但用户明确授权时仍可记录无评分引用的学习证据。

快速 capture 是不可变事实层，只保存题目身份、评分引用、用户已确认的正确步骤、第一个断点、后续不同断点、提示与修正、掌握证据、未解决点及逐项来源。相同身份与内容重跑为 `noop`；同一身份出现不同内容时失败关闭，不覆盖旧事实。完成状态是 `pending_nightly`，不能解释为正式卡和派生层已经收口。

夜间目标集由 `quick_intake.py pending --date YYYY-MM-DD` 回放得到，不依赖当前聊天是否仍保留完整历史；输出同时给出 active freeze，跨任务恢复必须复用，不能重复冻结同一 capture。只读查重和目标映射完成后，必须在任何正式写入前追加 `freeze`，固定 amendment 链、有效证据与目标哈希、新来源 artifact 和正式卡前哈希。夜间按真实题目聚合事件，一张卡只高质量改写一次；所有目标正式卡完成后只运行一次成功的 wrongnet rebuild，再完成定向回滚、SHADOW 关系提案和 Wiki ingest，并为每个正式目标物化答案安全教学切片。`closeout-v3` 先验证 `teaching_contexts` 与全部派生产物，再写不关闭 capture 的 prepare，最终复核后才 commit；全部通过才关闭，失败事件继续 pending 并在原 freeze 下幂等重试，正式状态已变化时不得重复 writer apply。`study_date` 保存学习事实和回滚日期，`artifact_date` 保存 wrongnet/Wiki 的实际构建日，因此允许隔天补做。freeze 后新增的无关 capture 留给后续批次；未写正式层的 freeze 可经用户确认安全 abort 后再 amend，同卡旧版本 capture 通过 source-verified rebase 恢复。历史 closeout-v2 保持只读兼容。

只有用户明确说“立即完整正式入库”“现在重建并回滚”或同义口令时，才同步执行 batch-size-one 的完整收口；仍必须先 capture，再用 `explicit_subset` freeze，并完成 formal、一次 rebuild、rollback、SHADOW、Wiki、visual、teaching context 与 closeout-v3，不能跳过两阶段合同。

## 学习后五道旧题

`intake_recommend.py --date YYYY-MM-DD --seed-id ID [--seed-id ID ...] --top N` 只接受用户明确确认的当日正式 ID，默认目标数量为 5。它对整组 anchors 只运行一次，并且只返回已经存在于正式错题库中的旧卡。

选择分两层：先匹配具体 `wrong_point`、第一错步或 `method_gap`；精确层不足时，再按两张正式卡共同持有的 `knowledge` 标签使用 `knowledge_fallback`。候选必须通过唯一正式卡、未掌握、第 8 天起可交付和“从未无提示独立做对”四道门禁。学习后筛题必须复用调度器的权威永久排除集合；4～5 分或明确无提示独立做对的历史触发，3 分不触发。两层不足时少出，不扫描全库猜 anchors，不用近期题补足。

数学系统不提供模型编写的纠错题、变式题或迁移题。用户口令中的“生成五道”只表示生成一份已有旧卡清单；明确要求 AI 编写新题时也失败关闭并改为提供旧卡筛选。筛选过程只读，不创建题面、答案、内部题包、队列 state 或作答日志，也不把合成题写入正式错题库。

D0 只保留为“当天学习阶段”的时间语义。当日旧题检查做对不能增加长期延迟成功次数；第二天或之后正式到期的独立闭卷检查才可按长期 `score` 规则推进。

## 长期 score

`scheduler.py score` 只允许在所有类型的长期单元正式到期后调用。复发当天、未排期或未到期单元均拒绝写入。

- 0～2 分：做错、无法启动、选错方法或明显提示后才完成；下次安排第二天。
- 3 分：可能是提示或纠偏后做对，也可能是结果明显不稳定；不得当作无提示独立做对，不推进长期阶段，只小幅增加间隔。
- 4～5 分：无提示独立闭卷做对并完成方法辨认；推进到下一长期阶段，并永久排除该实际作答卡的 warmup 交付。

`attempt_id` 与单元、日期一起生成稳定 `event_id`。幂等标记与单元在一次原子替换中写入，同事件重跑不再推进；若上次只缺长期 JSONL 记录，则只恢复日志。

## 考试日期边界

- 所有非空 `下次复习日期` 不得晚于 `2026-12-20`。
- 距考试 15～30 天时，高风险题最大间隔 7 天，其他不稳定题最大间隔 14 天。
- 距考试 14 天及以内，稳定题不进入新长期阶段，不把所有稳定题拉入最后一周。
- `下次复习日期` 决定错点 anchor 何时开始到期，不直接指定实际交付题；`调度优先级` 只决定到期 anchor 超容量时的先后顺序。
